## Task

Omnisearch is a mountable Rails engine (formerly the standalone
`omnisearch-rails` app, now archived) that gives a host app a `/search`
endpoint backed by Google or Bing, with pluggable providers and caching that
degrades to no-cache rather than failing.

The engine is complete and CI is green on all four jobs. What remains is
housekeeping and the decision below about whether this should be published to
RubyGems.

## Decisions

- **The repo is `~/Developer/omnisearch`, not `omnisearch-rails`.** The engine was
  built as a new gem rather than a restructure of the existing app, so there are
  two repos. `omnisearch-rails` is archived (`archived: true`), its issues #1 and
  #3 closed with pointers here.
- **The engine never calls `config.cache_store`.** `Omnisearch::Cache` reads
  whatever the host has for `Rails.cache`. The alternative — engine owning a
  cache — would impose a `cache` database on every host app, which is exactly
  the kind of assumption that makes an engine annoying to depend on.
- **Cache operations rescue and return nil.** An uncached search costs one
  upstream HTTP request; a raised exception costs the caller a 500.
- **Providers registered by class, looked up by declared name.** A host can
  override a built-in by registering a subclass under the same name, with no
  engine change. `engine: "both"` means every *registered* provider, not a
  hardcoded pair.
- **`error_messages` is always an array, never null**, including on success. A
  field that is sometimes-null and sometimes-not is one every client
  special-cases. This was the fix in the last `omnisearch-rails` PR (#21).
- **`.carrot.md` is committed to this repo.** It is public, and the working
  notes are a reasonable portfolio signal. Confirmed by the user.

## Tried and failed

**The RuboCop CI failure (`cannot load such file -- rubocop-rspec`).** Two
separate bugs, both mine, both invisible locally.

1. `Metrics/BlockLength` was declared twice in `.rubocop.yml`. YAML silently kept
   the last one and discarded the `test/**/*` exclusion. Fixed by merging into
   one key with both entries.
2. The real cause: **`AllCops: Exclude` replaces RuboCop's defaults rather than
   merging with them.** The default list is `node_modules`, `tmp`, `vendor`,
   `.git`. Setting `Exclude: ['dummy/**/*']` dropped `vendor/**/*`, so RuboCop
   walked into `vendor/bundle/.../gems/hashdiff-1.2.1/`, found *that gem's* own
   `.rubocop.yml` (whose first line is `require: rubocop-rspec`), and tried to
   load the plugin. HTTParty pulls in hashdiff, so it was in the bundle.

Why it passed locally and failed in CI: CI installs to `BUNDLE_PATH=vendor/bundle`,
which is the only place gem *sources* land on disk. A local bundle has
compiled gemspecs only, so there is no `.rubocop.yml` to find. To reproduce:

```console
$ git clone https://github.com/zarmeza/omnisearch.git && cd omnisearch
$ BUNDLE_PATH=vendor/bundle bundle install
$ BUNDLE_PATH=vendor/bundle bundle exec rubocop --parallel   # reproduces it
```

Two fixes that did **not** work, so they do not need retrying:

- Declaring `plugins:` explicitly in `.rubocop.yml` — still failed.
- `inherit_mode: { merge: [Exclude] }` — verified still 5 offenses, still the
  same load error. `inherit_mode` governs inheritance from other config files,
  not the replacement of the built-in defaults.

**Network is unreliable on this machine.** `git push` and `gh` calls fail
intermittently with `Could not resolve hostname github.com` or
`error connecting to api.github.com`. They succeed on retry. Wrap them rather
than treating the first failure as real.

## Open questions

- **Should the gem be published to RubyGems at all?** The README and gemspec
  both read as if it is available (`gem "omnisearch"` with no `github:` source).
  That is fine as a portfolio repo and wrong as a published gem until it is
  actually on RubyGems. Options: publish, or reword the install snippet to use
  `gem "omnisearch", github: "zarmeza/omnisearch"`.
- **`dummy/config/master.key` and `dummy/config/credentials.yml.enc` are
  gitignored**, deliberately, so the dummy app has no credentials on a fresh
  clone. CI passes, so the dummy does not need them. Unverified: whether
  `rails test` in `dummy/` behaves differently on a clean checkout than on this
  machine, which has the files present but unread.
- **Six stale branches on the archived `omnisearch-rails` repo** have work never
  merged into `develop`: `feature/rails-engine`, `feature/github-actions`,
  `feature/gitlab-ci`, `feature/rubocop`, `feat/solid-cache`,
  `fix/error-messages-key`. `feature/rails-engine` is the origin of this gem —
  it added `omnisearch-rails-engine` to the Gemfile. Left alone; deleting them
  is a user call.
