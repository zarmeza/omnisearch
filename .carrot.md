## Decisions

- **The repo is `~/Developer/omnisearch`, not `omnisearch-rails`.** The engine was
  built as a new gem rather than a restructure of the existing app, so there are
  two repos. `omnisearch-rails` is archived (`archived: true`), its issues #1 and
  #3 closed with pointers here.
- **The engine never calls `config.cache_store`.** `Omnisearch::Cache` reads
  whatever the host has for `Rails.cache`. The alternative — engine owning a
  cache — would impose a `cache` database on every host app, which is exactly
  the kind of assumption that makes an engine annoying to depend on.
- **Cache operations rescue and return nil.** An uncached search costs one
  upstream HTTP request; a raised exception costs the caller a 500.
- **Providers registered by class, looked up by declared name.** A host can
  override a built-in by registering a subclass under the same name, with no
  engine change. `engine: "all"` means every *registered* provider, not a
  hardcoded pair.
- **`error_messages` is always an array, never null**, including on success. A
  field that is sometimes-null and sometimes-not is one every client
  special-cases. This was the fix in the last `omnisearch-rails` PR (#21).
- **`.carrot.md` is committed to this repo.** It is public, and the working
  notes are a reasonable portfolio signal. Confirmed by the user.

### 2026-10-07, engine rename

- **`engine: "both"` is removed, not aliased.** The user chose to break
  compatibility: `omnisearch-rails` was a tech challenge for a job interview
  years ago, not a system running in production, so there is no caller to
  protect. `both` was a leftover word — the wildcard already meant every
  *registered* provider via `registry.names`. Canonical name is now `all`.
  **Do not restore `both` on backwards-compatibility grounds**; the reasoning
  for dropping it is above. README, CHANGELOG, AGENTS.md and this file all had
  to change because several of them claimed the contract carried over unchanged.
- **Normalization lives in `EngineSelection`, not `Query`.** `Query` had grown
  past `Metrics/ClassLength`, and turning an `engine` param into a validated
  list is a separable rule with no HTTP in it. `EngineSelection` owns
  `EVERY = :all`, normalization and validation; `Query` keeps the reader as
  `@selection.names` so nothing else had to change.
- **`Query#engine` reads back as the normalized Array.** Same rule as
  `error_messages`. `Query#providers` differs in exactly one case — it resolves
  the wildcard — and the two readers are documented against each other.
- **A list is all-or-nothing.** `engine=google,altavista` is 422 and searches
  nothing. Silently searching the recognized subset would leave a caller who
  asked for two engines with one and no way to tell.
- **`engine=all,google` is rejected** as self-contradictory, with a message
  pointing at `engine=all` alone.
- **Blank `engine` says `is required`; a Hash says `must be a provider name`.**
  `?engine[foo]=bar` arrives as a Hash, and "is required" would be a lie about
  what the caller did.
- **Both wire formats accepted**, comma string and `engine[]=`, so the Ruby API
  and the HTTP endpoint take the same shapes with no new param name. The
  `engine[]=` path is only reachable from a dummy integration test — unit tests
  call `Query` directly and never see Rails' param parsing.
- **`Metrics/ClassLength` now excludes `test/**/*`**, on the same reasoning as
  the existing `Metrics/BlockLength` exclusion. Splitting is still allowed when
  a test file stops being about one thing, which is why the list tests went to
  a new file instead of all 43 tests staying together.

### 2026-10-08, docs and deprecation cleanup

- **`lib/omnisearch/railtie.rb` is not renamed.** The file declares
  `class Engine < ::Rails::Engine`, and the layout block in `AGENTS.md` had
  invented both an `engine.rb` and a `lib/omnisearch/controllers/` directory,
  neither of which exists. Correcting the *doc* to match the tree was the
  smaller change, and renaming the file would mean touching `lib/omnisearch.rb`
  and the gemspec's file list for no functional gain. An agent reading the
  layout should also not "fix" the mismatch — `AGENTS.md` now says so, and
  records that `git log --follow` shows the two disagreed from the first commit,
  so the name is an unexplained slip rather than a deliberate leftover.
- **`SimpleCov.add_filter` → `SimpleCov.skip`.** Same arguments, same
  behaviour; only the call name changed. Verified by line coverage staying at
  exactly 258/265 before and after — had the filters silently stopped applying,
  the denominator would have moved. Chosen over leaving the deprecation because
  it was the only noise in an otherwise silent test run.

## Tried and failed

**The RuboCop CI failure (`cannot load such file -- rubocop-rspec`).** Two
separate bugs, both mine, both invisible locally.

1. `Metrics/BlockLength` was declared twice in `.rubocop.yml`. YAML silently kept
   the last one and discarded the `test/**/*` exclusion. Fixed by merging into
   one key with both entries.
2. The real cause: **`AllCops: Exclude` replaces RuboCop's defaults rather than
   merging with them.** The default list is `node_modules`, `tmp`, `vendor`,
   `.git`. Setting `Exclude: ['dummy/**/*']` dropped `vendor/**/*`, so RuboCop
   walked into `vendor/bundle/.../gems/hashdiff-1.2.1/`, found *that gem's* own
   `.rubocop.yml` (whose first line is `require: rubocop-rspec`), and tried to
   load the plugin. HTTParty pulls in hashdiff, so it was in the bundle.

Why it passed locally and failed in CI: CI installs to `BUNDLE_PATH=vendor/bundle`,
which is the only place gem *sources* land on disk. A local bundle has
compiled gemspecs only, so there is no `.rubocop.yml` to find. To reproduce:

```console
$ git clone https://github.com/zarmeza/omnisearch.git && cd omnisearch
$ BUNDLE_PATH=vendor/bundle bundle install
$ BUNDLE_PATH=vendor/bundle bundle exec rubocop --parallel   # reproduces it
```

Two fixes that did **not** work, so they do not need retrying:

- Declaring `plugins:` explicitly in `.rubocop.yml` — still failed.
- `inherit_mode: { merge: [Exclude] }` — verified still 5 offenses, still the
  same load error. `inherit_mode` governs inheritance from other config files,
  not the replacement of the built-in defaults.

**Network is unreliable on this machine.** `git push` and `gh` calls fail
intermittently with `Could not resolve hostname github.com` or
`error connecting to api.github.com`. They succeed on retry. Wrap them rather
than treating the first failure as real.

**An archived GitHub repository is read-only, which includes its branches.** The
four stale branches on `omnisearch-rails` could not be deleted while it was
archived: `git push origin :refs/heads/x` fails with `This repository was
archived so it is read-only`. The sequence that works is unarchive, delete, push
tags, re-archive:

```console
$ gh repo unarchive zarmeza/omnisearch-rails --yes    # --yes, or it prompts
$ git push origin 'refs/tags/archive/*'
$ git push origin ':refs/heads/feature/foo'
$ gh repo archive zarmeza/omnisearch-rails --yes
```

Note `gh repo unarchive` and `gh repo archive` both need `--yes` when
non-interactive, and they fail with a usage dump rather than an error message if
it is missing.

Those branches held work that never reached `develop`, so it was preserved as
annotated tags before deletion: `archive/github-actions`, `archive/gitlab-ci`,
`archive/rails-engine`, `archive/rubocop`. `feature/rails-engine` is where this
gem came from — it added `omnisearch-rails-engine` to the Gemfile. Tags survive
branch deletion, which is why they were pushed first.

**`app/models/search.rb` on `omnisearch-rails` still uses the deprecated
`%{value}` interpolation.** The `archive/rubocop` branch changed it to
`%<value>s`. Checked, not assumed: `Search.new(engine: "bogus").valid?` renders
correctly on `develop` under Rails 8.1, so this is a deprecation, not a live
bug. Not worth fixing in an archived repo, but it means `develop` there is not
lint-clean if anyone ever un-archives it.

**`Metrics/ClassLength` on `test_query.rb` was fixed by extraction, not by
suppression — but the test class is still 126 lines and growing.** Adding list
tests tipped it over. The extraction that actually helped was moving the
normalization rule out of `Query` into `EngineSelection`, which both satisfied
the cop on the lib side and gave the list tests a natural home. Suppressing
`ClassLength` on the test file alone would have hidden the signal that `Query`
had two jobs. If the test class gets much larger, split by subject the same way.

**`carrot-handoff save` silently deletes any `##` heading it does not recognize.**
Found this the hard way, and it nearly cost real content. The parser maps a
heading to a section by slug, so `## Decisions (2026-10-07, engine rename)`
parses to the key `other_decisions_2026_10_07_engine_rename` — an *extra*
section, not the canonical `decisions` one. `CLI#save` then calls
`Template.render`, which iterates `Record::SECTIONS` only. Extras are never
rendered, so the whole section vanishes. Measured: **49 lines lost in one save.**

This directly contradicts `record.rb`, whose comment on `extra_sections` says a
hand-written section "is never silently discarded on rewrite." It is preserved
through `load` and through `status` (which reports it as
`extra: decisions_2026_10_07_engine_rename`) and then thrown away at write time.

Two things follow. First, **use only the six canonical headings at `##` level**
— `Task`, `State`, `Decisions`, `Tried and failed`, `Next action`,
`Open questions` — and demote anything else to `###` inside one of them. That
is what the dated decisions block was converted to, so the save is now
idempotent. Second, **`carrot-handoff status` is the check to run before
trusting a save**: anything it lists under `extra:` is on its way out unless it
has been folded into a canonical heading first.

Reproduce in this repo with `.carrot.md` as committed at `d6d4292`:

```console
$ cp .carrot.md /tmp/carrot-backup.md
$ carrot-handoff save "demo"
$ diff /tmp/carrot-backup.md .carrot.md | grep -c '^<'
49
```

The fix belongs upstream in the gem, not in this repo: `Template.render` should
emit `record.extra_sections` after the canonical ones. Not filed — the gem is
yours and this is only worth doing if the bug is going to bite someone else.
